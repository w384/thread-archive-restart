# 设计说明（Design）

本文记录 thread-archive-restart 的阈值口径、测量模型与关键设计决策，面向维护者与想调参的使用者。

## 背景

长任务 agent 会话会持续累积 input tokens。上下文窗口接近满载后，模型回复质量下降、早期决策被遗忘、token 成本上升。业界主要有两类做法：

- 上下文压缩 / 记忆管理（如上下文工程、TencentDB-Agent-Memory 等长任务记忆方案）：在会话内保留更多有效信息；
- 线程归档重开：用新线程承接旧线程的工作，前提是"交接"不丢信息。

本技能属于后者，并强调"半自动 + 交接包优先"，避免"归档即丢失"。

## 数据模型与测量口径

- 数据源：`$CODEX_HOME/sessions/**/rollout-*.jsonl`，只取 `type=event_msg` 事件行。
- 累计 input：最近一条 `token_count` 的 `info.total_token_usage.input_tokens`（含重放）。
- 最近一轮增量：从最近一次 `user_message` / `task_started` 轮次边界起，到最后一次 `token_count` 的累计增量。
- 窗口占用：`last_token_usage.input_tokens / model_context_window`。
- rollout 文件大小：该线程所有 `rollout-*.jsonl` 的最大文件字节数。

## 阈值设计

| 信号 | 阈值 | 依据 |
|---|---|---|
| TRIGGER（单轮增量） | ≥ 200,000 tokens | 一轮输入出现 20 万级激增，说明单次任务已远超常规单轮体量，属于"本轮任务完成后应归档"的典型信号。 |
| ARCHIVE（累计 input） | ≥ 10,000,000 tokens | 千万级累计意味着会话已跨越大量轮次，长期维护成本高于重开收益。 |
| ROLLOUT（文件体积） | > 5 MB | rollout 为 JSONL 明文，5MB 约对应数万条事件，读取与解析成本显著上升。 |
| WARN（窗口占用） | ≥ 80% | 接近窗口上限时质量开始下降，作为预警而非强制。 |

## 关键设计决策

1. **半自动，不自动归档**。归档是不可逆的用户动作，任何检测都只通知；执行必须由用户确认。这是安全边界，不会因阈值误判造成数据损失。
2. **交接包优先**。归档前先把状态写入共享交接包（状态基线 / git 基线 / 剩余待办 / 关键决策 / 风险），归档只是"把细节移出常驻层"，不是删除。
3. **`--check` 退出码**。把判定结果编码进进程退出码（0/1/2/3/4），使 cron、CI、提交前钩子等外部系统可以零解析地消费结果。
4. **零依赖、可测**。测量脚本只用 Python 标准库；`--sessions` 允许指向任意目录，便于用合成 fixture 做确定性测试。
5. **隐私优先**。脚本只做本地读取与聚合输出，不发网络请求；README 与 SECURITY 明确 rollout 文件不得入库。

## 局限与后续

- 阈值是启发式默认值，可用 CLI 参数覆盖；不同模型上下文窗口差异大，WARN 阈值建议按实际窗口调整。
- 当前只做"判定 + 流程指引"，交接包草稿生成（`--summary`）列为路线图。
- rollout 事件结构若随 Codex 版本变化，需同步更新 `analyze_thread` 的字段解析。
